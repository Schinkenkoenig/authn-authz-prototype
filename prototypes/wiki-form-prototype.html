Per-paradigm prose

Full axis content per paradigm — abbreviated here to two examples so the shell is visible.

RBAC — Role-Based Access Control

grant grain: per-role · config surface: DB rows

Users are assigned roles; roles carry permissions. The workhorse of enterprise authz because many users share a few roles, so onboarding is a single row.

user_roles: bob → editor, erin → editor, carol → viewer, dave → admin role_permissions: editor → projects/ (Read,Write,List) viewer → shared/ (Read,List) admin → * (Read,Write,List)
Upsides
  • reuse — add a user to a role, inherit everything
  • onboarding is one row
Downsides
  • coarse; fine-grained → role explosion
  • no per-resource nuance, no context

ReBAC — Relationship-Based Access Control (OpenFGA / Zanzibar)

grant grain: per-relation · config surface: model + tuples

Access follows relationships in a graph: ownership, group membership, folder-hierarchy inheritance. Expresses "editors of a folder are editors of everything beneath it" as composable edges.

type prefix relations define parent: [prefix] define editor: [user, team#member] or owner or editor from parent define viewer: [user, user:*, team#member] or editor or viewer from parent
Upsides
  • native hierarchies, groups, ownership
  • one edge cascades down a subtree
Downsides
  • external engine + graph-shaped thinking
  • the model is its own artifact to version

…abac, claims, acl, cedar, opa sections follow the same shape…

Apples-to-apples — one scenario, seven configs

The world. Prefix projects/ is eng-editable; shared/ is public-read. The eng team is {bob, erin}, carried by attribute department=engineering. carol is an outsider; alice is a public reader.

Same verdict under all seven — so what differs is only the config an admin must write:

ProbeRequestVerdictExercises
P1erin write projects/plan.mdpermitgroup
P2alice read shared/notes.txtpermitpublic / everyone
P3carol write projects/plan.mddenybounded

Two axes carry the divergence: group membership (RBAC/ABAC/ReBAC express reuse; ACL/claims enumerate per member) and "everyone" (ACL *, ReBAC user:*, ABAC empty-condition = one artifact; RBAC and claims have no wildcard principal).

The idle context/deny-override in Cedar & OPA is itself the finding: for a decision this simple the policy engines are overkill — they earn their keep only in sweet-spot mode.

Stack — a separate axis (this mock can't settle it; your call)

Recommendation: NOT the existing Next.js SPA. It sits behind Keycloak login (a read-only public wiki shouldn't require a sign-in) and is pinned to a deliberately-weird Next version the SPA's AGENTS.md warns against. The comparison content already lives as markdown under docs/.

That leaves two live options: (1) render the markdown with a static-site generator, or (2) a standalone static site (like this file). Both are public, buildable, decoupled from the SPA.

Coupled open question (map fog "where does config-surface data come from"): a fetch-capable stack (SSG with client JS, or the SPA) keeps the door open to pulling config live from GET /authz/{paradigm}/config; a pure static export forecloses it and commits to hand-authored content. Pick the stack knowing which door it shuts.
